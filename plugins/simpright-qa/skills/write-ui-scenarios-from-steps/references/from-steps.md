# From steps: UI scenarios from the user's test steps

Read by the `simpright-qa:ui-scenario-writer` agent when the `/simpright-qa:write-ui-scenarios-from-steps` skill starts it with **Steps**. The scope is the user's test cases. The agent's rules, "Prepare", "Look at the app", "Writing steps" and phases still apply, with "criterion" meaning one of these test cases and "the document" the user's text.

- **Split the text into test cases:** numbered or titled cases, or one sequence of actions with its expected results each. For each, note the starting state, the actions and the expected results, as for a criterion.
- **One scenario per test case,** from the agent's checklist ("Choosing scenarios") applied to that case only: no boundaries or extra cases the user didn't write (mention obvious gaps once under "Decisions needed"). A case that checks unrelated things (two different flows, each with its own result) is proposed split, as a decision.
- **Keep the user's wording and order;** change only what the conventions need, and say in the proposal when you changed more than wording:
  - the state the user starts from ("Go to the home page", "Log in as admin", "Have a product in the cart") becomes `preconditions` (statements) and `role`, unless doing it is what the case tests;
  - one user action per step, with the labels as the app shows them (the inspector says which);
  - expected results become `Verify` steps, one concern each, about something a user can see; an expected result a user can't see is handled as in the checklist's "Make every outcome observable";
  - secret values become descriptions ("the default user's email"), record ids and URLs become what the user sees.
- **App vs steps:** the inspector shows something else than the steps say (another label, a missing control, another message) → a decision, as in "Look at the app": a possible bug (the scenario asserts the steps and gets a proposed `knownIssue` and `bug`) or outdated steps (the scenario follows the app). When an existing scenario has the same start and actions but expects something else, it isn't "already covered": it's the same decision, naming that scenario, and "possible bug" then means changing it (its `Verify` steps, plus `knownIssue` and `bug`) instead of adding a new one, because two scenarios must never assert opposite results. Make that change in the `write` phase only when the user explicitly approves it (the exception to the agent's rule 2).
- **Near duplicates:** a case that repeats an existing scenario with only another role or other data (another category, another product) is proposed, with a decision naming that scenario: keep it as extra coverage, or drop it. An example check the user gives next to a broader expectation ("only hammers, e.g. "Claw Hammer" is shown") stays a check of its own.
- **API first:** a case whose check only proves a server rule (a field limit, a validation, a calculation) and that the API could check faster goes under "Decisions needed" as "could be an API scenario (`/simpright-qa:write-api-scenarios-from-steps`)". Propose it on the UI anyway; the user decides.
- **`ref`** is the brief's `Ref`; with "none", leave `ref` out.
- **Proposal:** the "Criterion (ref)" column becomes "Source" (the test case's number or title in the user's text), and the "Criteria map" becomes a "Steps map": each test case, its scenarios, and what wasn't turned into a scenario and why.
