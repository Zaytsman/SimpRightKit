# The SimpRight Kit's CI part

GitHub Actions composite actions for a Playwright project, plus the workflows `simpright apply` writes from `simpright.yml` to use them. Together they run the tests on GitHub's runners, publish every run to the [portal](../packages/portal) on GitHub Pages, keep the portal's Test Cases and Bugs pages current, and publish a wiki.

| Action | What it does |
|---|---|
| [`setup`](setup/action.yml) | Node.js with the npm cache, `npm ci --ignore-scripts`, an optional private registry for one scope, and the Playwright browsers (cached) |
| [`run-tests`](run-tests/action.yml) | `playwright test` for a project (`ui`, `api` or `all`), narrowed to paths and a grep; then, optionally, the step-title check (warnings only) |
| [`publish-run`](publish-run/action.yml) | The run's report onto the `gh-pages` branch, with the newest runs kept and the dashboard refreshed (`simpright-portal publish-run`) |
| [`publish-pages`](publish-pages/action.yml) | The Test Cases pages, the Bugs page and the dashboard onto `gh-pages` (`simpright-portal build-pages`) |
| [`squash-pages`](squash-pages/action.yml) | The `gh-pages` history squashed into one commit holding the same site |
| [`publish-wiki`](publish-wiki/action.yml) | A folder of Markdown pages copied to the repository's GitHub wiki |

Each `action.yml` describes its inputs. Every action takes `working-directory` (default `.`), for a project in a subfolder of its repository.

## Using the actions

Pin each action to the commit of a kit release, with the version in a comment, as for any third-party action:

```yaml
- uses: actions/checkout@<sha> # v7.0.1
  with:
    persist-credentials: false
- uses: Zaytsman/SimpRightKit/actions/setup@<commit of v0.2.0> # v0.2.0
  with:
    node-version: 24
```

- The workflow checks out the project first; the actions install and run what they find there.
- The publish actions call the project's own `simpright-portal`, so the project has `@simpright/portal` as a devDependency (`setup` installs it), at the version of the actions.
- `run-tests` reads the project's Playwright reports: the HTML report in `playwright-report/` and the JSON report in `test-results/results.json` (Playwright's `html` and `json` reporters). The step-title check needs `@simpright/scenarios`.
- A repository that allows only selected actions (Settings → Actions → General) needs the kit's actions on its list, for example `Zaytsman/SimpRightKit/actions/*`.

## The workflows `simpright apply` writes

```bash
npx simpright apply --dry-run   # show the changes
npx simpright apply             # write them
```

From `simpright.yml` (the [`simpright`](../packages/simpright) package documents the keys):

| File | When | What |
|---|---|---|
| `.github/workflows/playwright-run.yml` | `runs` | The reusable test job: setup, typecheck, `run-tests`, `publish-run` (with a portal), the report as an artifact |
| one caller per run (`runs[].workflow`, default `<id>.yml`) | `runs` | The run's schedule, project, grep, paths and runs kept; an `areaPicker` run gets an area input listing its test folders |
| `.github/workflows/pr-checks.yml` | always | The `verify` job: typecheck, `simpright-scenarios validate`, `simpright doctor`, the portal's page build |
| `.github/workflows/publish-test-cases.yml` | `parts.portal` | The portal's pages, on pushes to the default branch that change the scenarios, the bugs, `simpright.yml` or the lockfile |
| `.github/workflows/squash-gh-pages.yml` | `parts.portal` | The monthly squash (04:45 UTC on the 1st) |
| `.github/workflows/publish-wiki.yml` | `parts.wiki` | `paths.wiki` to the wiki, on pushes that change it |
| `.github/dependabot.yml` | always | Weekly updates with a 7-day cooldown, to `ci.branches.work` when there is one; one pull request moves the kit's packages and its actions together |

Each file starts with a "Generated by simpright apply" line. `apply` keeps a hash of what it wrote in `.simpright/state.json` and stops, showing the diff, before it overwrites a file someone changed (`--force` overwrites). A Dependabot pin bump isn't a change: the hashes leave the pins out, and `apply` keeps a third-party pin that's newer than its own. `simpright doctor` fails while the files differ from what `apply` would write, so `verify` catches a forgotten `apply` (a new run, a new test folder, a new kit version).

A run's file name is fixed once its workflow has run: GitHub numbers a workflow's runs per file, and the portal keeps a family's highest run numbers. A renamed caller would start again at run-1.

## The rules they follow

The kit's actions and the generated workflows follow these rules; a workflow you write by hand should too.

- Every action is pinned to a full commit SHA, with its version in a comment (`actions/checkout@<sha> # v7.0.1`), in workflows and in `action.yml` files. Dependabot updates both.
- Every checkout sets `persist-credentials: false`. Only the steps that push get a token: their `token` input, which has no default, so a workflow shows which step can push.
- `npm ci` runs with `--ignore-scripts`: no dependency's install script runs, above all while a registry token is set.
- Inputs reach `run:` scripts through `env:`, never as `${{ }}` inside the script.
- A reusable workflow declares the secrets the tests read, and callers pass them by name (`ci.secrets`), never `secrets: inherit`.
- A workflow that installs a private package from GitHub Packages needs `packages: read`, in the reusable workflow and in every caller.
- Schedules start off the full hour (:15, :45): GitHub's queue is busiest on the hour.
- The default token is read-only; a job asks for `contents: write` only when it pushes.

## How the kit tests them

The kit's [e2e workflow](../.github/workflows/e2e.yml) runs these actions on the sample project on every pull request and push to `main`. It installs the sample, runs its smoke tests and the step-title check, publishes the run and the pages to the kit's own `gh-pages` branch (which nothing serves), checks the files there, then squashes the branch and checks it's one commit with the same files. `publish-wiki` is left out: it would overwrite the kit's wiki.
